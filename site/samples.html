Sample projects

Every sample is synthetic and every step in it is a command the product actually runs. No sample contains patient data, and none has been edited to look better than it ran. The transcripts below were captured from the built executable on the current branch; the exact text can change as output changes, and the tests, not this page, are what hold each sample to the product.

1. The synthetic evaluation walkthrough

One shell script, ten steps, one new directory: inspect, generate, verify, capture, index, diagnose, diff, validate a regression spec locally, run it against fresh loopback fixtures, and verify the sealed packet. It is in the repository at samples/synthetic-walkthrough, and TestSyntheticWalkthroughCompletesEveryStepAgainstTheBuiltExecutable runs the same file in CI.

go build -trimpath -o readmit ./cmd/readmit
sh samples/synthetic-walkthrough/walkthrough.sh

2. The fail, pass, fail regression demonstration

Two terminals: one runs the fixture receiver in defective mode, then fixed mode, then defective again; the other runs the same unchanged spec against each. The baseline fails on the ledger count, the fix passes, and reintroducing the defect fails again. This is the demonstration report --scenario automates; the manual procedure, with its reset instructions, is in the test runner documentation, and TestTestExecutableUnchangedSpecFailsPassesAndCatchesReintroduction runs it.

3. Redact and export a synthetic case

Capture the committed redact-booking.mllp and redact-reschedule.mllp fixtures, apply the committed policy, review the export, and watch the blocked policy refuse. The scenario and the fixtures ship in every archive; the procedure is in the redaction documentation, and TestRedactExecutableGeneratesOnlyDerivedProofAndNoPlantedValues runs it.

4. The guided sample in the desktop shell

The desktop shell's Create sample workspace action writes the same seed-zero case bundles the walkthrough generates, byte for byte, into a new readmit-sample folder and opens it. It is written as a workspace rather than a family: the family.json completion record is not kept, because nothing may be written inside retained evidence, and two entries that are not evidence are written beside the cases — a loopback practice endpoint, so a test has a target to name, and a states-only index of the sample case, so the message grid can be opened without readmit index build. TestDesktopSampleWorkspaceHoldsTheCommandLineFamilyBytes holds the generated bytes to the command line's output.

From there the whole investigation is finished in the window, with nothing typed into a shell: author a regression test over the sample case, run it against a practice receiver the application binds on a loopback port of the same machine and watch it fail on the fixture's defect, then run the same spec against the corrected receiver and watch it pass. The case, the spec and both results are ordinary artifacts the command line reads, and where you are in the path is read back out of the folder rather than remembered. TestTheGuidedSampleIsCompletedThroughTheWindowAlone completes every step through the application facade and reads the result back with the built executable. No desktop package is signed for distribution, so this is a path through a shell built from a checkout, not one an engineer installs today. There is no screenshot of it yet; see limitations, and the guided sample for what none of it establishes.

What the samples cannot show

None of them touch a database, an integration engine, a vendor endpoint or a customer export, because readmit does not implement the first two and the samples must run anywhere with nothing but the executable. A sample against your own export directory is the source collect workflow with your paths, and the source documentation walks through it.
