Download

Release status: unsigned development preview. Three different things are easy to confuse, so this page keeps them apart: what is published (an early prerelease containing readmit inspect only), what CI builds and installation-tests on every push (the current branch, as unsigned CLI archives and unsigned native desktop packages that are never published), and a published complete product (which does not exist yet; release acceptance is open). Nothing is code-signed for distribution or notarized; an operating-system or endpoint policy may refuse to run any of it.

The published candidate: v0.1.0-alpha.2

The only published archives are the v0.1.0-alpha.2 GitHub prerelease, built from an early commit that shipped readmit inspect alone. Every other workflow described on this site landed on main afterwards and is in no published archive. Treating the prerelease as the product would understate the current code and overstate the release; this page does neither.

Archives, checksums.txt and build provenance are published only on GitHub Releases. Each archive holds one static executable with no runtime, installer or container requirement, plus the README, the documentation pages, third-party notices and licenses, the field-label source, and synthetic fixtures.

sha256sum readmit_0.1.0-alpha.2_linux_amd64.tar.gz        # Linux
Get-FileHash .\readmit_0.1.0-alpha.2_windows_amd64.zip -Algorithm SHA256   # Windows
# compare with the matching line of checksums.txt, then extract and run:
tar -xzf readmit_0.1.0-alpha.2_darwin_arm64.tar.gz

GitHub build provenance is attested for each published executable and is separate from OS code signing. With the GitHub CLI: gh attestation verify ./readmit --repo bharm16/readmit (or readmit.exe).

Desktop packages

The desktop shell is distributed as each platform's own package, never inside a CLI archive. On every push, CI builds each package natively on its target runner, installs it through the platform's own installer, checks the installed application, and removes it — so the packaging is exercised, while no package and no installer is published anywhere and no window is opened on any runner, because no runner has a display. Every build writes a readmit-desktop-package/v1 manifest beside the packages naming each package, its format and its SHA-256 digest, and recording "signed_for_distribution": false.

No package downloads a prerequisite, reaches a network, or installs a service, daemon or scheduled task. Verification re-reads the manifest strictly, re-computes every digest, and opens each package with the tools that wrote it; a manifest claiming a distribution signature is refused by name. Signed and notarized installers are selected in the product decisions and remain a release gate — this page's table is the whole truth of the current state, and it is not that future state.

Build from source

To evaluate the workflows on this site before the next tagged prerelease, build from source with the pinned Go 1.27.1 toolchain. The build is static, needs no C compiler, and produces one file.

git clone https://github.com/bharm16/readmit
cd readmit
go build -trimpath -o readmit ./cmd/readmit
./readmit --help
sh samples/synthetic-walkthrough/walkthrough.sh

The desktop shell is a separate Wails 2 module over the same engine; building it additionally needs Node 24 and a platform webview. The procedure is in the README, and the packaged result is what the section above describes. A source build is a preview you built yourself — it is not a published release, and it establishes no acceptance of its own.

What CI checks on every push, so you can read its verdict instead of taking this page's word for it: the race-enabled Go suite, an independently implemented HL7 endpoint against an externally authored corpus, mutation checks, fuzz shards, a vulnerability scan, packaging of the five archives, the desktop packages above, and a native run of each archived executable with an empty PATH. The workflows are ci.yml and desktop.yml; the local loop is in the README.

Not included

  • No installer, service, daemon, scheduled task, shell integration or PATH change for the command line: you extract a directory and run a file. The desktop packages use each platform's own installer and declare exactly what the table above lists.
  • No update check. A newer version is a new archive or package you choose to download.
  • No account, activation or entitlement. Every workflow here runs without one. readmit license verifies an offline entitlement file when an organization has been issued one; none is required to evaluate.
  • No telemetry, crash reporting or analytics, and this site carries none either.
  • No support offering, published license terms or evaluation program yet. The support matrix states this in full.

Upgrading and removing

Evidence directories are versioned strict-JSON files and raw payloads that a newer executable reads through explicit contract versions; a version it does not read is refused, never migrated in place. To upgrade the command line, extract the new archive beside or over the old executable. To remove it, delete the directory; it wrote nothing anywhere else except the evidence and documents you asked it to write, and the desktop shell's named local documents described in the desktop contract. The desktop packages uninstall through the platform's own installer, and removing the application leaves evidence and project documents wherever you kept them.
